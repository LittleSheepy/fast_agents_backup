# FastAgents《XX 模块编写说明》模版 v2.0

> 本模版用于统一 `fast_agents` 各模块说明文档的结构与写法，目标是做到「**翻开任何一份模块说明，都知道在哪一节能找到什么**」。
> 适用模块：`tools` / `memory` / `skills` / `mcp`，以及后续新增的 `context` / `infra` 等。
> 使用方法：把文中的 `XX` 换成模块中文名，按每节给出的「写什么 / 要点 / 示例」逐节填充。

**v2.0 相对 v1.0 的三处变更**

1. **「平台专项（Windows）」不再独立成章**，并入第十节「设计决策与常见坑」，作为其下的「跨平台注意事项」小节；该模块没有平台差异时，这一小节**整节删除**；
2. **章节标题按模块微调**（骨架不动）：第二章、第三章、第六章的标题允许换成贴合本模块的措辞，模版在每处都给出了四个模块的实际标题做参照；
3. **章节编号与已交付文档对齐**：开篇（文档头部 + 目录）→ 一～十三 → 附录，和 `Skill模块编写说明.md` / `工具模块编写说明.md` / `记忆模块编写说明.md` / `MCP模块编写说明.md` 四份成品完全一致。

### 0.2 标记约定

- `● 必备`：任何模块都要写，缺一节即视为文档不完整；
- `○ 按需`：按模块特性决定是否保留，不适用就整节删除；
- `【写什么】`：这一节要回答的问题；
- `【要点】`：容易写砸的地方，逐条对齐；
- `【示例】`：可照抄的格式样例，`[...]` 为占位内容。

## 一、更新历史 ●

```markdown
> **v[N] 更新摘要**（本次同步）
> 1. **[变更点]** —— [为什么改 / 怎么迁移]；
> 2. **[变更点]** —— [同上]。
>
> **v[N-1] 更新摘要**（上一版）
> 1. **[变更点]** —— [同上]。
```

【写什么】倒序记录每一版对**使用者可见**的变更。
【要点】

1. **只写使用者会感知的变更**：改名、删除、行为变化、默认值变化。内部重构不写（那是 git log 的事）；
2. 每条固定格式「`[改了什么]` —— `[为什么 / 怎么迁移]`」，**必须给迁移办法**。参考记忆模块的写法：写明「旧 import 路径 → 新 import 路径，参数完全一致」，读者照着改就行；
3. 第一版可以没有本节，从第二次迭代开始补齐。

## 二、先想清楚：XX 解决什么问题 ●

【写什么】在贴任何代码之前，先把**概念分层**和**设计目标**立住。这是全篇的地基——地基不清，后面每一处设计都讲不通。
【要点】

1. 用一个问题开场，逼出分层。例如记忆模块的「Agent 的记忆到底分几种」、tools 的「好工具层要做到什么」；
2. 给一张**分层表**，字段固定为：`层级 / 生命周期 / 存储位置 / 典型内容 / 本框架对应`；
3. 提炼 **2–5 条「关键设计原则」**，并声明「后面代码都在落实它们」——后续每一处设计都要能回指某一条原则，形成闭环。

【示例】记忆模块的分层表可照抄结构：

| 层级 | 生命周期 | 存储位置 | 典型内容 | 本框架对应 |
|---|---|---|---|---|
| 工作记忆 | 单次会话 | 内存 | 最近 N 轮、当前任务状态 | `BufferMemory` |
| 情景记忆 | 跨会话 | 数据库 | 发生过的事 | `MemoryRecord(kind="episode")` |
| … | | | | |

【示例】tools 模块的写法是列 8 条设计目标（四种定义方式 / 结构化返回值 / 参数校验 / 多 provider schema / 输出保护 / 错误标准化 / 异步 / 可观测）。

## 四、模块架构 ●

### 4.1 目录结构

```markdown
fast_agents/[模块]/            ← 单数目录，对齐 tools/ memory/ skills/ mcp/
├── __init__.py               模块出口（统一导出）
├── [文件].py                 [一行职责]
└── ...
```

【要点】

1. **目录一律单数**（`skill/` 而非 `skills/` 指模块目录；技能包本身用复数 `skills/` 是另一回事，要说清区别）；
2. 每个文件后面跟一行职责注释，**不要只画树不说职责**；
3. 明确标注哪些是**新增**、哪些是**修改既有文件**。

### 4.2 分层 ●

【写什么】把模块内的文件按职责分层（出口层 / 抽象层 / 实现层 / 适配层…），说清层与层之间的依赖方向。

### 4.3 数据流 / 调用链路 ●

【写什么】一张 ASCII 图，串起「用户输入 → 各组件 → 输出」的主链路；复杂模块给 2–3 张（如记忆模块的读写双链路、MCP 的接入与调用）。
【要点】箭头旁标注方法名（如 `memory.retrieve()`），让读者能顺藤摸瓜到源码。

### 4.4 与 ReActAgent 的接入点 / 职责边界 ●

【写什么】

1. 这个模块**怎么挂进 Agent**（构造参数 / 成员变量 / 初始化方法）；
2. 与相邻模块的**单一数据源约定**——边界不清就会出 bug。参考记忆模块把 `self.messages` 与 `memory.buffer` 的职责边界单列一节讲透，这是全篇最值钱的段落之一。

【要点】对齐 `ReActAgent` 既有约定：system 只注入一次、tool 链不进 buffer、跨轮历史只有 `MemoryManager.buffer` 一个数据源。

## 五、核心机制：XXX ○（弹性节，每模块认领）

> 本节是留给「模块特有内容」的弹性位：**标题和内容形态由模块自己定，但位置固定在第五章**，不另起炉灶、也不挤进别的节里。四个模块的认领见 0.4 表。

| 模块 | 本节标题 | 典型要讲的内容 |
|---|---|---|

【要点】

1. 用一张**维度对比表**呈现（维度 / 方案A / 方案B），并给出「什么场景选哪个」的明确建议；
2. **不要两边都夸**，要有倾向、有结论；
3. 若本模块没有值得一提的特有机制，**整节删除**，但要在 0.4 认领表里注明「不适用」。

## 七、逐个文件讲解（源码导读） ●

【写什么】每个源码文件一小节，固定三段：**它负责什么 → 关键实现 → 为什么这么写**。

## 十、设计决策与常见坑 ●

> 本章是「为什么」的集中地，也是**跨平台差异的唯一落点**。三块固定顺序：关键设计决策 → 常见坑与排查 → 跨平台注意事项。

### 10.1 关键设计决策（为什么）

【写什么】3–5 条「为什么不选另一种做法」。参考 tools 模块的「为什么 `invoke()` 还要再校验一次」「为什么错误默认 catch 而不是 raise」。

### 10.2 常见坑与排查

```markdown
| 现象 | 原因 / 解决 |
|---|---|
| [...] | [...] |
```

【要点】把实测踩过的坑**全部**列进来（串数据、token 爆炸、tool 链被拆坏、缓存失效、中文乱码、路径空格…）。每条必须是「现象 + 可执行解法」，不能只写现象。

### 10.3 跨平台注意事项（Windows 专项）○

> **这是 v2.0 从旧独立章节并入的内容**：不再单列章节，只作为本章最后一小节。**本模块没有平台差异时，整个 10.3 删除**，不要为凑小节写「无」。

【写什么】本模块在 Windows 上的差异点，逐条给可执行解法：

1. **路径空格**：整段命令串 + `shlex.split(cmd, posix=False)`；
2. **编码**：子进程注入 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`，读取用 `errors="replace"`；
3. **子进程黑框**：`CREATE_NO_WINDOW`；
4. **换行符**：`.py`/`.md`/`.bat` 用 CRLF、`.sh` 必须 LF，靠 `.gitattributes` 统一（LF 入库、Windows 检出 CRLF）；
5. **脚本解释器**：`.py` 走 `sys.executable`、`.ps1`/`.bat` 走 `powershell -ExecutionPolicy Bypass -File`、`.sh` 走 `bash`；
6. **控制台编码**：打印中文乱码时的两行修法。

【示例】MCP 模块这一小节实写了六条专项，可直接对照它的粒度。

```markdown
| 测试文件 | 项数 | 覆盖点 | 运行命令 |
|---|---|---|---|
| `test/test_[模块].py` | [N]/[N] | [列举覆盖点] | `python test\test_[模块].py` |
```

【要点】

1. 逐条列出覆盖点（对齐现有做法：编号列出 9–11 项）；
2. **单独点名「关键回归断言」**及其锁住了什么设计——如记忆模块的 `test_no_duplicate_history_injection` 锁死「单一数据源」不被后续改动破坏；
3. 给出全绿基线，让读者知道「跑成什么样才算对」；
4. 若存在「测试与实现不同步」的情况，**如实写明**（哪个测试文件红、为什么红、该怎么改），不要粉饰。
