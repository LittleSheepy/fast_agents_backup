# 工具模块（Tools）编写说明

本文档面向 fast_agents 工具系统，参考 **LangChain BaseTool/StructuredTool**、**CrewAI BaseTool**、**LlamaIndex FunctionTool**、**Anthropic Tool Use** 等框架的共性设计，给出新架构的完整说明、源码解析和自定义工具教程。
> 版本：v2 · 2026-10-26 · 清理所有兼容层，统一对齐 LangChain/LangGraph/CrewAI/LlamaIndex 命名惯例。
> 适用版本：`fast_agents.tools`

## 一、设计目标

工具是 Agent 与外部世界交互的唯一入口。一个好的工具层要做到：

1. **四种定义方式共存**：简单场景写得快，复杂场景有扩展性——继承、装饰器、工厂、裸函数任选其一；
2. **结构化返回值**：不能只返回裸字符串——Agent 需要知道「成功/失败/截断」三类状态，决定继续/重试/缩小查询；
3. **参数校验自动化**：pydantic 全量校验，错误消息要对 LLM 友好（让它能自纠正）；
4. **多 provider schema**：一份定义，自动生成 OpenAI / Anthropic / Gemini 三套 function-calling schema；
5. **输出保护**：结果过长自动截断，防止一次性读爆上下文；
6. **错误处理标准化**：异常转为可恢复的错误消息，不让 LLM 看到 raw traceback；
7. **异步友好**：`invoke/ainvoke` 同步异步双入口；
8. **可观测性**：三级 hook（before/after/on_error）给 tracing、审计、日志留扩展点；
9. **零依赖兼容**：核心只依赖 `pydantic`，docstring 解析是可选增强（装了 `docstring_parser` 才启用）。

## 二、模块结构

```
fast_agents/tools/
├── __init__.py          # 统一导出：ToolBase / StructuredTool / tool / ToolResult /
│                        #            ToolStatus / ToolException / ToolRegistry / global_registry / builtin
├── tool_base.py         # ToolBase 抽象基类（核心）
├── structured_tool.py   # StructuredTool（函数→工具） + @tool 装饰器
├── tool_result.py       # ToolResult / ToolStatus：结构化执行结果
├── tool_exception.py    # ToolException / ToolInitializationError / ToolPermissionError
├── tool_registry.py     # ToolRegistry：工具注册表 + 执行入口
└── builtin/             # 内置工具集合
    ├── __init__.py
    ├── calculator_tool.py   # 安全数学计算器（AST 白名单）
    ├── terminal_tool.py     # 受限 shell
    ├── search_tool.py       # DuckDuckGo / Tavily 联网搜索
    └── read_file_tool.py    # 带沙箱的本地文件读取
```

记忆工具不在 tools 目录，而在 `fast_agents/memory/tool.py`（因为它依赖 `MemoryManager`），通过 `from fast_agents.memory import build_memory_tools` 统一获取。

## 三、核心数据模型

### 3.1 ToolStatus / ToolResult（tool_result.py）

所有工具执行最终都会返回 `ToolResult`：

```python
@dataclass
class ToolResult:
    output: str = ""              # 给 LLM 看的人类可读字符串
    status: ToolStatus = SUCCESS  # SUCCESS / ERROR / TRUNCATED
    error: Optional[str] = None   # 失败时的错误信息
    artifact: Any = None          # 结构化数据，供下游工具/记忆使用
    is_error: bool = False

    ToolResult.ok(output, artifact=None)            # 成功
    ToolResult.fail(error_msg)                      # 失败
    ToolResult.truncated(output, orig_len, limit)   # 截断（自带提示语）
```

Agent 在拿到 `ToolResult` 后会根据 `status` 给观察文本加前缀：
- `SUCCESS` → 直接输出原文；
- `ERROR` → 前缀 `[工具执行错误]`，提示模型「检查参数或换方式重试」；
- `TRUNCATED` → 输出已自带「输出已截断，可缩小查询范围」的提示。

### 3.2 ToolException（tool_exception.py）

```python
class ToolException(Exception):
    message: str
    observation: str   # 给 LLM 看的提示，默认 = message
    tool_name: str     # 出错工具名
```

当工具内部想让错误**可恢复**（即让模型看到 observation 后自纠正，而不是直接把错误往上抛），抛 `ToolException` 即可；其他普通异常在 `handle_tool_error=True` 时会被统一捕获转成 `ToolResult.fail(...)`。

## 四、四种定义工具的方式（从快到全）

### 方式 1：`@tool` 装饰器 —— 90% 场景首选

```python
from fast_agents.tools import tool

@tool
def roll_dice(sides: int = 6) -> str:
    """掷骰子
    Args:
        sides: 骰子面数，默认6
    """
    import random
    return f"掷出了 {random.randint(1, sides)}"

@tool(name="web_search", description="联网搜索网页，返回标题/链接/摘要",
      max_output_chars=5000, tags=["search"])
def search(query: str) -> str:
    ...
```

参数 schema 从类型注解 + `Args:` docstring 自动推导；名字默认取函数名，描述默认取 docstring 第一段。

### 方式 2：`StructuredTool.from_function` —— 工厂方法

适合需要传 API key 等运行时参数的工具：

```python
from fast_agents.tools import StructuredTool

search = StructuredTool.from_function(
    search_func,
    name="web_search",
    description="联网搜索",
    max_output_chars=5000,
    tags=["search"],
)
```

### 方式 3：继承 `ToolBase` —— 带内部状态时用

```python
from pydantic import BaseModel, Field
from fast_agents.tools import ToolBase, ToolResult

class WeatherInput(BaseModel):
    city: str = Field(description="城市名")
    units: str = Field(default="celsius", description="celsius/fahrenheit")

class WeatherTool(ToolBase):
    name = "weather"
    description = "查询指定城市的天气"
    args_schema = WeatherInput            # ⚠️ 注意：是 args_schema，不是 param_model
    tags = ["weather"]                    # 可选：分类标签

    def __init__(self, api_key: str):
        super().__init__(max_output_chars=8000)
        self.api_key = api_key

    def run(self, city: str, units: str = "celsius"):
        data = self._fetch(city, units)
        return ToolResult.ok(
            f"{city}: {data['temp']}°",
            artifact=data,               # 结构化数据给下游用
        )
```

类属性约定（均可选，均有合理默认）：

| 属性 | 类型 | 说明 |
|---|---|---|
| `name` | `str` | 工具名（必须唯一，给 LLM 看的标识符） |
| `description` | `str` | 告诉 LLM 什么时候用这个工具，要写得具体 |
| `args_schema` | `Type[BaseModel]` | 参数模型；不提供则从 `run()` 签名自动推导 |
| `max_output_chars` | `int` | 输出字符上限，超出自动截断（默认 100_000） |
| `handle_tool_error` | `bool` | 异常自动捕获成失败结果（默认 True） |
| `tags` | `list[str]` | 分类标签，方便 `registry.filter_by_tag()` |
| `metadata` | `dict` | 任意元数据 |
| `return_direct` | `bool` | 结果是否直接返回给用户（不进入下一轮推理，适用于最终答复类工具） |

> ⚠️ **v2 命名变更**：旧版叫 `param_model`，现在统一叫 `args_schema`，对齐 LangChain BaseTool 的属性名。如果你的子类还在用 `param_model`，请改为 `args_schema`。

### 方式 4：直接注册裸函数 —— 最懒写法

```python
registry = ToolRegistry()
registry.register_tool(lambda x: f"echo: {x}")   # name 取函数名 lambda 不行，请用 def 命名函数
```

裸函数会被自动包装成 `StructuredTool`。

## 五、核心 API 参考

### 5.1 ToolBase（实例方法）

| 方法/属性 | 返回 | 说明 |
|---|---|---|
| `invoke(tool_input=None, **kwargs)` | `ToolResult` | 同步执行，带参数校验 + 错误捕获 + 自动截断 |
| `ainvoke(tool_input=None, **kwargs)` | `ToolResult` | 异步执行（需要实现 `arun`） |
| `run(**kwargs)` | `str` / `ToolResult` | 子类实现，业务逻辑 |
| `arun(**kwargs)` | `str` / `ToolResult` | 子类实现异步版本（可选） |
| `input_schema` | `dict` | **property**：返回当前工具的 JSON Schema（自动去 `$ref`/`title`） |
| `to_openai_tool()` | `dict` | 生成 OpenAI function-calling schema |
| `to_anthropic_tool()` | `dict` | 生成 Anthropic tool schema |
| `to_gemini_tool()` | `dict` | 生成 Gemini function declaration |

**调用 `invoke` 支持两种写法**（对齐 LangChain Runnable 接口）：

```python
tool.invoke(a=1, b="x")                    # 关键字参数
tool.invoke({"a": 1, "b": "x"})            # 单一 dict
tool.invoke('{"a": 1, "b": "x"}')          # JSON 字符串（LLM 调用时用这种）
```

> ⚠️ **v2 命名变更**：
> - 旧 `param_model` → 新 `args_schema`；
> - 旧 `args_schema()` **方法** → 新 `input_schema` **属性**（注意不要加括号）；
> - 旧 `build_openai_tool()` / `build_anthropic_tool()` / `build_gemini_tool()` → 新 `to_openai_tool()` / `to_anthropic_tool()` / `to_gemini_tool()`（前缀 `to_` 是 Python 序列化惯例，与 registry 的 `to_openai_tools()` 对称）。

### 5.2 ToolRegistry（工具注册表）

```python
from fast_agents.tools import ToolRegistry
reg = ToolRegistry()

# ── 注册 ──────────────────────────────────
reg.register_tool(WeatherTool(api_key))        # 单个
reg.register_tools(t1, t2, func3)              # 批量
reg.unregister("weather")                      # 删除

# ── 查询 ──────────────────────────────────
reg.get_tool("weather")                        # → ToolBase / None
reg.has_tool("weather")                        # → bool
reg.list_names()                               # → ["weather", ...]
reg.list_tools()                               # → [ToolBase, ...]
reg.filter_by_tag("builtin")                   # 按标签筛选
reg.get_tools_description()                    # 给 system prompt 用的多行字符串

# ── 执行（统一入口）───────────────────────
result: ToolResult = reg.invoke_tool("weather", {"city": "上海"})
result: ToolResult = reg.invoke_tool("weather", '{"city": "上海"}')
result: ToolResult = reg.invoke_tool("weather", city="上海")   # kwargs 追加
print(result.output, result.status, result.artifact)

# ── Schema 导出（多 provider）────────────
reg.to_openai_tools()      # 传给 OpenAI chat.completions.create(tools=...)
reg.to_anthropic_tools()
reg.to_gemini_tools()

# ── Hook ──────────────────────────────────
reg.add_hook(lambda name, args, result: print(f"[trace] {name}({args}) → {result.status}"))

# ── 运算符 ────────────────────────────────
tools = calc + terminal + search   # 等价于 OpenAI tools 列表
```

> ⚠️ **v2 删除**：旧的 `execute_tool(name, arguments) -> str` 是历史兼容层，已删除。统一改用 `invoke_tool(name, tool_input, **kwargs) -> ToolResult`；如果只想要字符串，取 `.output` 即可。

### 5.3 全局注册表 `global_registry`

```python
from fast_agents.tools import global_registry
```

一个预创建的 `ToolRegistry` 单例，快速原型时用；生产项目建议自己 new 一个，避免命名冲突。

## 七、完整范例：给 ReActAgent 装上工具 + 记忆

```python
from fast_agents import LLM, ReActAgent, ToolRegistry
from fast_agents.tools import builtin
from fast_agents.memory import MemoryManager, build_memory_tools

llm = LLM()
registry = ToolRegistry()
registry.register_tools(
    builtin.CalculatorTool(),
    builtin.TerminalTool(workspace="."),
    builtin.SearchTool(),
    builtin.ReadFileTool(workspace="."),
)

memory = MemoryManager(llm=llm, user_id="default")
for t in build_memory_tools(memory):
    registry.register_tool(t)

agent = ReActAgent("助手", llm, tool_registry=registry, memory=memory)
agent.run("1+2*3 等于几？同时帮我记住我偏好中文回答")
```

## 八、设计决策与坑

### 8.1 为什么 `$ref` 必须内联

pydantic v2 对嵌套 BaseModel / Enum 会生成 `{"$ref": "#/$defs/Xxx"}`，而 OpenAI 等 provider 对 `$defs` 支持不完整（很多模型直接丢弃 `$defs` 段）。如果不内联，嵌套字段会变空对象，模型看不到参数结构 → 瞎填 → 参数校验失败 → 工具调用死循环。`tool_base._pydantic_to_json_schema` 里的 `_resolve` 专门处理了这事，并处理了「`$ref` + 兄弟键（description/default）」的合并。

### 8.2 为什么工具结果用 ToolResult 而不是直接 str

三个原因：
1. Agent 需要区分「失败」和「成功但输出很长被截断」——后者应该引导模型缩小查询；
2. `artifact` 携带结构化数据，下游工具可以直接用（不必从 output 字符串里 parse），记忆系统也可以直接存 artifact；
3. 失败时有统一的 `error` 字段，hook/tracing 好过滤。

### 8.3 为什么错误默认 catch 而不是 raise

Agent 循环里一个工具抛异常如果直接冒泡，整个 Agent 就挂了。更合理的行为是把错误当成一条「观察」返回给模型，让它自纠正（换参数、换工具）。确实需要中断时可以：
- 传 `handle_tool_error=False`；
- 或在工具内部抛特殊异常由外层捕获。

### 8.4 为什么参数自动校验很重要

LLM 经常会：
- 漏必填字段；
- 把数字传成字符串；
- 给枚举字段传了枚举外的值。

如果没有参数校验，这些错会在工具内部以各种奇怪形式爆出（KeyError、TypeError），模型看不懂 raw traceback。`ToolBase.invoke` 用 pydantic 校验后，把错误转成「`city` 字段必填」「`units` 必须是 celsius/fahrenheit」这种中文提示，模型看到就能自纠正。

### 8.5 `+` 运算符的小心思

`ToolBase.__add__` 让你可以写 `tools = calc + terminal + search`，直接得到 OpenAI 格式的 list。混合 list 也支持：`[calc] + terminal`、`terminal + [calc]` 都合法。
