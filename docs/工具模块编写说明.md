## 二、先想清楚：Tools 解决什么问题

### 2.1 一句话概括

**工具是 Agent 伸向外界的「手」。**

模型本身只会生成文本。要让它查天气、读文件、算数、跑命令，就得把这些能力封装成**模型能理解、能安全调用**的单元——这就是工具。

工具模块要解决四件事：

| 问题 | 解决手段 |
|------|---------|
| 模型怎么知道有哪些工具、怎么传参？ | `to_openai_tool()` / `input_schema`，生成标准 JSON Schema |
| 不同 provider 的 schema 格式不一样怎么办？ | 三个导出方法：OpenAI / Anthropic / Gemini |
| 工具执行会失败、会返回巨长文本，怎么不炸掉 Agent？ | `ToolResult` 三态 + `max_output_chars` 截断 + `handle_tool_error` |
| 一堆工具怎么统一管理？ | `ToolRegistry` |

### 2.2 设计目标（`tool_base.py` 文件头写的 8 条）

这个模块的注释里明确列了 8 条设计约定，值得先记住：

1. **四种定义方式共存**：继承类 + `args_schema` / `@tool` 装饰器 / `StructuredTool.from_function` / 纯函数内省；
2. **结构化返回值**：`run()` 可返回 `str` 或 `ToolResult`；`invoke()` / `ainvoke()` 统一返回 `ToolResult`；
3. **多 provider schema**：`to_openai_tool` / `to_anthropic_tool` / `to_gemini_tool`（`to_` 前缀是 Python 序列化惯例）；
4. **参数级描述**：通过 `Field(description=...)` 或 docstring 的 `Args:` 段自动提取；
5. **结果自动截断**：`max_output_chars` 控制；
6. **同步/异步双入口**：`run` / `arun`（子类实现），`invoke` / `ainvoke`（带校验、错误处理、截断的公共入口）；
7. **hooks 机制**：`before_run` / `after_run` / `on_error`；
8. **`handle_tool_error` 开关**：决定工具内部异常是抛出去还是包成失败结果。

## 三、主流框架 Tools 实现对比

### 3.1 对比总表

| 框架 | 工具基类 | 函数式包装 | Schema 生成 | 返回值协议 | 多 provider |
|------|---------|-----------|------------|-----------|------------|
| **LangChain** | `BaseTool` | `@tool` / `StructuredTool.from_function` | `args_schema`（pydantic v2）+ `model_json_schema()` | `ToolMessage` / `ToolException` | 各家集成包各写一份 |
| **CrewAI** | `BaseTool` | `@tool` | `args_schema`（pydantic） | 裸字符串为主 | 由 LLM 适配层处理 |
| **LlamaIndex** | `BaseTool` | `FunctionTool.from_defaults` | pydantic / 函数签名 | `ToolOutput` | — |
| **Semantic Kernel** | `KernelFunction` | `@kernel_function` | 函数注解 + 元数据 | `FunctionResult` | — |
| **OpenAI Agents SDK** | `FunctionTool` | `@function_tool` | 自动从签名 + docstring | — | 仅 OpenAI |
| **Anthropic** | Tool Use API | 直接传 dict | JSON Schema | `tool_result` block | 仅 Anthropic |
| **fast_agents** | `ToolBase`（ABC） | `@tool` / `StructuredTool.from_function` | 显式 `args_schema` **或**签名内省 | **`ToolResult` 三态 + `artifact`** | **内置三个导出方法** |

### 3.2 三个关键差异

**① 返回值协议：多数框架只给字符串，fast_agents 给了三态**

LangChain 的工具返回值最终会被塞进 `ToolMessage`，CrewAI 也基本是字符串。问题在于：**Agent 无法从字符串本身判断这次调用是成功还是失败、是不是被截断了**。

`fast_agents` 的做法是引入 `ToolStatus` 三态（`success` / `error` / `truncated`），再配一个 `artifact` 字段存原始结构化数据。好处：

- Agent 读到 `truncated` 就知道该缩小查询范围再试一次，而不是拿着半截输出硬答；
- 下游代码（记忆、审计、评测）可以直接读 `artifact`，不用去正则解析字符串。

**② Schema 生成：多了一条「函数签名内省」路线**

LangChain 的 `StructuredTool` 也支持从函数签名建 schema，但对不写类型注解、不写 docstring 的函数没辙。`fast_agents` 的 `_infer_param_schema_from_signature()` 做了更宽松的处理：

- 没有类型注解 → 默认按 `string`；
- `Optional[X]` / `Union[X, None]` → 取非 None 的那个类型；
- `Literal[...]` → 生成 `enum`；
- `Enum` 子类 → `string`；
- 嵌套 `BaseModel` → `object`；
- docstring 参数描述优先用 `docstring_parser` 解析，**装不上就降级**手工扫 `Args:` 段。

**③ `$ref` 展开：这是 fast_agents 一个很实的改进**

pydantic v2 的 `model_json_schema()` 对于嵌套模型、枚举，会生成 `{"$ref": "#/$defs/Xxx"}` 加一个独立的 `$defs` 块。**很多 provider 对 `$ref` 支持不完整**，有的直接把 `$defs` 丢掉，结果模型看到的参数结构就是一堆悬空引用。

`_pydantic_to_json_schema()` 做了两件事：

1. **递归展开 `$ref`**，把 schema 压成自包含的扁平结构。关键细节：不能加 `len(node) == 1` 的判断——pydantic 在字段带 `description` / `default` 时会生成 `{"$ref": ..., "description": ...}`，只判长度会漏掉，而 `$defs` 已经被 pop 掉了，最终留下悬空 `$ref`。
2. **剥掉 `title` 字段**，它对模型没有信息量，只占 token。
3. **循环引用保护**：用 `seen` 元组记录已展开的模型名，遇到自引用就返回 `{}`，避免无限递归。

`test_tools.py` 里专门有一条用例 `test_nested_ref_expansion`（嵌套模型 `$ref` 展开）在守这个行为。

### 4.3 一次工具调用的完整链路

```text
Agent 拿到 LLM 返回的 tool_call: {"name": "python_calculator", "arguments": "{\"expression\": \"2+3\"}"}
  │
  ├─ registry.invoke_tool(name, tool_input)        # tool_registry.py
  │    ├─ 取 tool，找不到 → ToolResult.fail("未找到名为 ... 的工具")
  │    ├─ 字符串 → json.loads → dict；解析失败 → ToolResult.fail
  │    └─ tool.invoke(**kwargs)                     # tool_base.py
  │         ├─ _validate_args()  ← args_schema(**kwargs)，ValidationError → ToolResult.fail("参数错误：...")
  │         ├─ _before_run()
  │         ├─ run(**validated)  ← 子类实现，可能返回 str 或 ToolResult
  │         │    └─ 抛异常 → _on_error() → handle_tool_error ? ToolResult.fail : raise
  │         ├─ _coerce_result()  ← str → ToolResult.ok
  │         ├─ 超 max_output_chars → ToolResult.truncated()
  │         └─ _after_run()
  │
  └─ 逐个执行 registry 的 hooks(name, kwargs, result)
```

## 五、核心机制：四种工具定义方式

这是本模块最灵活的地方：**同一个工具，四种写法。**选哪个取决于场景。

### 方式一：继承 `ToolBase` + 显式 `args_schema`

适合参数复杂、需要严格校验、或者有额外初始化逻辑的工具。

```python
from typing import Union
from pydantic import BaseModel, Field
from fast_agents.tools import ToolBase, ToolResult


class WeatherInput(BaseModel):
    city: str = Field(description="城市名，如 '上海'")
    days: int = Field(default=1, ge=1, le=7, description="预报天数 1-7")


class WeatherTool(ToolBase):
    name = "weather"
    description = "查询指定城市未来几天的天气。当用户询问天气、气温、是否下雨时使用。"
    args_schema = WeatherInput
    tags = ["api", "weather"]

    def run(self, city: str, days: int = 1) -> Union[str, ToolResult]:
        if not city.strip():
            return ToolResult.fail("城市名不能为空")
        return ToolResult.ok(f"{city} 未来 {days} 天晴", artifact={"city": city, "days": days})
```

仓库里的 `builtin/` 五个工具全是这种写法。

### 方式二：`@tool` 装饰器

适合参数简单、逻辑就是一段函数的工具。装饰器会把函数自动包成 `StructuredTool`。

```python
from fast_agents.tools import tool


@tool(
    name="reverse_text",
    description="把一段文本倒序输出。当用户要求反转文字、倒着念时使用。",
    tags=["text"],
)
def reverse_text(text: str) -> str:
    """把文本倒序。

    Args:
        text: 要反转的文本
    """
    return text[::-1]
```

要点：

- **函数名默认就是工具名**（`name=` 不传时）；
- **`description` 不传时**，取 docstring 的**第一段**（按 `\n\n` 切）；
- **参数描述**从 docstring 的 `Args:` 段自动抽（走 `docstring_parser`）；
- 返回值可以是 `str`，也可以是 `ToolResult`。

### 方式三：`StructuredTool.from_function()`

和 `@tool` 是同一个东西，只是调用形式不同——`@tool` 内部就是转调它。适合**运行时动态**从函数造工具（比如从插件里读函数再包装）。

```python
from fast_agents.tools import StructuredTool

tool_obj = StructuredTool.from_function(
    my_func,
    name="my_func",
    description="……",
    max_output_chars=5000,
)
```

`from_function` 还支持 `coroutine=` 传入异步实现，这样 `arun()` 会走协程而不是线程池。

### 方式四：裸函数直接注册（内省）

`ToolRegistry.register_tool()` 会检测到「可调用但不是 `ToolBase`」，自动包成 `StructuredTool`：

```python
from fast_agents.tools import ToolRegistry

registry = ToolRegistry()

def add(a: int, b: int) -> str:
    """把两个数相加。

    Args:
        a: 第一个加数
        b: 第二个加数
    """
    return str(a + b)

registry.register_tool(add)     # 自动包装，工具名 = "add"
registry.register_tools(add, another_func)   # 批量
```

### 四种方式怎么选

| 场景 | 推荐方式 |
|------|---------|
| 参数多、要严格校验、要初始化状态（如 `workspace`） | 方式一（继承） |
| 一行逻辑的小工具，阶段固定 | 方式二（`@tool`） |
| 运行时从别处拿到函数再包装 | 方式三（`from_function`） |
| 快速试验、不想写样板 | 方式四（裸函数） |

> 四种方式产出的都是 `ToolBase` 实例，能力完全一致——**schema 生成、截断、错误处理、hook 全部生效**。

## 六、核心数据模型

### 6.1 `ToolResult`（`tool_result.py`）

工具执行的统一返回值，`@dataclass`。

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `output` | `str` | `""` | 给模型看的文本 |
| `status` | `ToolStatus` | `ToolStatus.SUCCESS` | 三态 |
| `error` | `Optional[str]` | `None` | 错误信息 |
| `artifact` | `Any` | `None` | 原始结构化数据，供下游消费 |
| `is_error` | `bool` | `False` | 冗余标记，`failed` 会参考它 |

**三个构造器**：

```python
ToolResult.ok(output, artifact=None)              # status=SUCCESS
ToolResult.fail(error)                            # output = f"错误：{error}"，status=ERROR，is_error=True
ToolResult.truncated(output, original_length, limit)
```

`truncated` 会追加一段提示：

```text
[⚠️ 输出已截断：原始 {original_length} 字符，已返回前 {limit} 字符。可使用更精确的查询缩小范围。]
```

并把 `artifact` 设成 `{"truncated": True, "original_length": ..., "limit": ...}`。

**两个属性**：

- `succeeded` → `status == SUCCESS`
- `failed` → `status == ERROR or is_error`

`__str__` 返回 `output`。

### 6.2 `ToolStatus`（`tool_result.py`）

```python
class ToolStatus(str, Enum):
    SUCCESS = "success"
    ERROR = "error"
    TRUNCATED = "truncated"
```

> 注意：`truncated` **不算失败**——`succeeded` 为 `False`（因为 status 不是 SUCCESS），`failed` 也为 `False`。这是一种「成功了但不完整」的中间态。

### 6.3 `ToolException`（`tool_exception.py`）

```python
class ToolException(Exception):
    def __init__(self, message, *, observation=None, tool_name=None):
        ...
        self.message = message
        self.observation = observation or message   # 给模型看的观察文本
        self.tool_name = tool_name                  # 出错的工具名
```

另外两个：

- `ToolInitializationError(Exception)`：初始化阶段失败；
- `ToolPermissionError(ToolException)`：权限不足。

> 这三者目前定义齐全，但 `ToolBase.invoke()` 的 `except Exception` 会**无差别捕获**，并不区分是不是 `ToolException`。`observation` 字段暂时没有代码去读。换言之，异常类型目前更多是语义标记。

### 6.4 `ToolBase` 的类属性与构造参数

| 类属性 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `name` | `str` | `""` | 工具名，空则 `raise ValueError` |
| `description` | `str` | `""` | 描述，空则 `raise ValueError` |
| `args_schema` | `Optional[Type[BaseModel]]` | `None` | 不提供则从 `run()` 签名内省 |
| `max_output_chars` | `int` | `100_000` | 超出则截断 |
| `handle_tool_error` | `bool` | `True` | `False` 时异常向上抛 |
| `tags` | `List[str]` | `[]` | 分类标签，`filter_by_tag` 用 |
| `metadata` | `Dict[str, Any]` | `{}` | 自定义元数据 |
| `return_direct` | `bool` | `False` | 直接返回模式标记 |

`__init__` 的参数与上表同名（全部 `Optional`），语义是「传了就用传的，没传就退回类属性」。所以 `ToolBase.__init__(name=None, description=None, ...)` 不传也不会报错，会取类属性。

> 一个真实的坑：`ToolBase` 是**普通 ABC，不是 pydantic BaseModel**。所以类属性 `tags: List[str] = []` 不能写成 `Field(default_factory=list)`——那样类属性会变成 `FieldInfo` 对象。代码里为此专门写了 `list(tags) if tags is not None else list(type(self).tags or [])` 来做拷贝，避免可变默认值共享。

## 七、逐个文件讲解

### 7.1 `tool_base.py`（381 行，最长）

**模块级辅助函数**（都在类外）：

| 函数 | 作用 |
|------|------|
| `_annotation_to_json_type(annotation)` | 把 Python 类型注解映射成 JSON Schema 的 `type`。处理 `Union`（取非 None 分支）、`list` / `List`、`dict` / `Dict`、`Literal`、`Enum`、嵌套 `BaseModel`；兜底 `string` |
| `_infer_param_schema_from_signature(func, skip=("self",))` | 从函数签名 + docstring 造 JSON Schema。参数描述优先 `docstring_parser`，`ImportError` 时降级手工扫 `Args:` 段 |
| `_pydantic_to_json_schema(model)` | pydantic → 扁平 JSON Schema，展开 `$ref`、剥 `title`、防循环引用 |

**`ToolBase` 的方法分组**：

*执行入口*

| 方法 | 说明 |
|------|------|
| `run(*args, **kwargs)` | **抽象方法**，子类必须实现 |
| `arun(**kwargs)` | 异步执行，默认用 `run_in_executor` 跑 `_run_safe` |
| `_run_safe(**kwargs)` | 内部同步包一层 |

*公共入口（带全套保护）*

| 方法 | 说明 |
|------|------|
| `invoke(tool_input=None, **kwargs) -> ToolResult` | 支持 `invoke(a=1)` 和 `invoke({"a": 1})` 两种写法；`tool_input` 是 JSON 字符串也会被解析 |
| `ainvoke(tool_input=None, **kwargs) -> ToolResult` | 异步版 |

`invoke` 的完整处理顺序（很重要，出事的时候按这个顺序排查）：

```text
tool_input 归一化（str → json.loads → dict；非法 → ToolResult.fail）
  → _validate_args（有 args_schema 就 model_dump）→ ValidationError → ToolResult.fail("参数错误：...")
  → _before_run(validated)
  → run(**validated)  ← 异常走 _on_error，handle_tool_error=False 就 raise
  → _coerce_result(raw)   ← str/None → ToolResult.ok
  → 超长则 ToolResult.truncated(...)
  → _after_run(validated, result)
  → return result
```

*内部辅助*

| 方法 | 说明 |
|------|------|
| `_validate_args(kwargs)` | 有 `args_schema` 就 `args_schema(**kwargs).model_dump()`，否则原样返回 |
| `_format_validation_error(e)` | 把 pydantic 的 `errors()` 拼成 `「字段」错误信息；…` 的中文串 |
| `_coerce_result(raw)` | `ToolResult` 原样返回；其他转 `ToolResult.ok(str(raw))` |
| `_before_run` / `_after_run` / `_on_error` | 三个 hook 点，默认实现只打日志 |

*Schema 与导出*

| 成员 | 说明 |
|------|------|
| `input_schema`（property） | 有 `args_schema` 用它，否则从 `run` 签名内省 |
| `to_openai_tool()` | `{"type": "function", "function": {name, description, parameters}}` |
| `to_anthropic_tool()` | `{"name", "description", "input_schema"}` |
| `to_gemini_tool()` | `{"name", "description", "parameters": {type, properties, required?}}` |

> 注意 Anthropic 用的键叫 **`input_schema`**，而 OpenAI 用 **`parameters`**。写适配层时容易搞混。

*运算符*

`__add__` / `__radd__` 支持工具与工具、工具与列表相加，产出的是 **OpenAI 格式的 dict 列表**——也就是 `to_openai_tool()` 的结果，不是工具对象。

```python
combined = tool_a + tool_b          # [openai_a, openai_b]
combined = tool_a + [openai_x]      # [openai_a, openai_x]
combined = [openai_x] + tool_a      # 走 __radd__
```

`test_tools.py` 里有对应用例（`tool+tool` / `list+tool`）。

### 7.2 `structured_tool.py`（130 行）

- `_get_type_hints_safe(func)`：`get_type_hints` 失败（比如有前向引用解析不了）时返回 `{}`，不抛异常。
- `_create_args_schema_from_function(func, name, skip=("self",))`：用 `pydantic.create_model` 动态造一个 `<name>_Args` 模型。没默认值的字段必填，有默认值的带 `default`。
- `StructuredTool(ToolBase)`：`__init__(func, name, description, args_schema=None, coroutine=None, max_output_chars=100_000, handle_tool_error=True, tags=None, metadata=None, return_direct=False)`；`run()` 直接转调 `self.func(**kwargs)`；`arun()` 有 `coroutine` 就走协程，否则退回 `super().arun()`。
- `from_function(...)`：**既可以当普通方法用，也可以当装饰器用**。判断依据是第一个位置参数 `func` 是否为 `None`。
- `tool(...)`：比 `from_function` 更薄的包装，多了 `handle_tool_error` 的传递控制。

> **细节点**：`from_function` 的签名里**没有 `handle_tool_error` 之外的 `metadata` 参数**（`metadata` 只在 `StructuredTool.__init__` 里有），而 `tool()` 装饰器也**没有暴露 `handle_tool_error` 和 `metadata`**。需要这两个就得直接用 `StructuredTool(...)` 构造。

### 7.5 `builtin/` 五个工具

#### `python_calculator`（`calculator_tool.py`）

- **工具名是 `python_calculator`，不是 `calculator`**——这点很容易记错。
- `args_schema = CalculatorInput`，只有一个字段 `expression: str`。
- 实现方式是 **AST 白名单求值**，不是 `eval`：`ast.parse(expr, mode="eval")` → 逐节点递归 `_eval()`。
- 白名单：
  - 二元运算 `ast.Add/Sub/Mult/Div/Pow/BitXor/FloorDiv/Mod`
  - 一元运算 `ast.USub/UAdd`
  - 函数 `abs/round/max/min/sum/sqrt/sin/cos/tan/log/log2/log10/exp/ceil/floor`
  - 常量 `pi`、`e`
- 返回 `ToolResult.ok(f"{expression} = {formatted}", artifact={"value":..., "expression":...})`；整数结果会去掉 `.0`。

> ⚠️ **已知行为不一致**：`description` 里写「支持基本运算（+ - * / ^）」，但 `_BINOPS` 把 `ast.BitXor` 映射到了 `operator.xor`——也就是说 `^` 是**按位异或**，`2^10` 会得到 8 而不是 1024。如果想支持幂运算，要么把 `^` 预处理成 `**`，要么把 description 里的 `^` 改成 `**`。测试 `test_tools.py::test_calculator` 目前就是这个失败项。

#### `terminal`（`terminal_tool.py`）

- 构造参数：`TerminalTool(workspace=".", timeout=30, max_output_chars=20_000, allow_exec=False, allow_cd=True, allowed_commands=None)`。
- 命令白名单：默认只放 `_READONLY_COMMANDS`（`ls`/`dir`/`pwd`/`tree`/`cat`/`head`/`tail`/`wc`/`find`/`grep`/`rg`/`sort`/`uniq`/`cut`/`awk`/`sed`/`diff`/`echo`/`which`/`whereis`/`whoami`/`cd` 等）。传 `allow_exec=True` 才把 `_EXEC_COMMANDS`（`python`/`python3`/`node`/`bash`/`sh`/`pip`）加进去。
- **沙箱**：`workspace` 会 `resolve()`，`_handle_cd` 用 `new_dir.relative_to(self.workspace)` 拦住逃逸；`_exec` 把 `cwd` 锁在当前目录，并把环境变量 `HOME` 改成 workspace。
- **`cd` 是特殊处理的**：它不真的起子进程，只是改 `self._cwd`。`reset()` 可以复位。
- 含管道 / 重定向 / 通配符 / `&&` / `;` 的命令会走 `shell=True`，其他走 `shell=False` 的列表形式。

#### `web_search`（`search_tool.py`）

- 构造参数：`SearchTool(provider="duckduckgo"|"tavily", api_key=None, max_output_chars=8000)`。
- `SearchInput`：`query: str`、`max_results: int = 5`（范围 1–20）。
- `duckduckgo` 走 `duckduckgo_search.DDGS`，`tavily` 走 `tavily.TavilyClient`——两个都是**延迟导入**，缺依赖时返回 `ToolResult.fail("缺少依赖：... 请安装：pip install ...")`，不会在模块导入期就炸。
- 输出格式：`序号. 标题` + `URL:` + 摘要，`artifact` 带原始结果列表。

#### `read_file`（`read_file_tool.py`）

- 构造参数：`ReadFileTool(workspace=".")`。
- `ReadFileInput`：`path: str`、`start_line: int = 1`、`end_line: Optional[int] = None`、`max_lines: int = 200`（范围 1–2000）。
- **沙箱**同上，用 `relative_to(workspace)` 拦越界。
- `_BINARY_EXTS` 是一个黑名单（图片 / 压缩包 / 可执行文件 / 音视频 / Office 文档），命中就拒绝读取。
- 读文件用 `encoding="utf-8", errors="replace"`（**不会因编码问题崩，但会出替换符**）。
- 输出带行号，格式是 `{行号:>5}|{内容}`，头部有 `📄 {path}  (共 N 行，显示 x-y 行)`，没读完会提示把 `start_line` 设成 `stop + 1`。

> 注意 `stop` 的计算：`min(end_line or (start + max_lines - 1), total, start + max_lines - 1)`——**即使显式传了 `end_line` 大于 `max_lines`，也会被 `max_lines` 截住**。

#### `remember_memory` / `recall_memory` / `forget_memory`（`memory_tool.py`）

三个工具，都要构造时传一个 `MemoryManager`：

| 工具名 | 参数 | 行为 |
|--------|------|------|
| `remember_memory` | `content: str`、`kind: str = "fact"`、`importance: float = 0.5` | `manager.remember(...)`，非法 `kind` 静默改成 `fact`，`importance` 被夹到 `[0,1]` |
| `recall_memory` | `query: str`、`limit: int = 5` | `manager.retrieve(query, limit)`，空结果返回「记忆库中没有找到相关信息。」 |
| `forget_memory` | `memory_id: str` | 支持 **前 8 位简写**（`startswith` 匹配），走 `manager.forget()` 软删除 |

外加一个便捷函数：

```python
def build_memory_tools(manager) -> list:
    return [RememberTool(manager), RecallTool(manager), ForgetTool(manager)]
```

> ⚠️ **这个文件的 docstring 写错了导入路径**。开头示例写的是：
>
> ```python
> from fast_agents.memory import MemoryManager, build_memory_tools
> ```
>
> 但 `build_memory_tools` 其实导出在 `fast_agents.tools.builtin`，`fast_agents/memory/__init__.py` 里**没有**它（也没有 `RememberTool` / `RecallTool` / `ForgetTool`）。正确写法是：
>
> ```python
> from fast_agents.memory import MemoryManager
> from fast_agents.tools.builtin import build_memory_tools
> ```
>
> `test/test_memory.py` 就是照着 docstring 写的，所以一上来就 `ImportError`。见 [10.6](#106-坑记忆工具与测试的导入路径)。

## 十、设计决策与常见坑

### 10.1 为什么 `invoke()` 还要再校验一次

`run()` 已经被子类实现了，为什么不在外面直接调 `run()`？

因为 `run()` 是「裸的」——它可能：参数类型不对、内部抛异常、返回超长文本。这三件事如果不管，一个写坏的工具就能把整轮对话搞崩。所以 `invoke()` 是**带护栏的入口**：校验 → 前后 hook → 异常兜底 → 截断。子类只需要专心实现 `run()`。

**推论**：自己写代码调用工具时，**永远走 `invoke()` / `registry.invoke_tool()`，不要直接调 `run()`**。

### 10.2 坑：计算器的 `^` 是异或不是幂

见 [7.5](#75-builtin-五个工具)。`description` 里宣传 `^` 支持幂运算，实际是异或。这是**文档与实现不一致**，不是测试写错。要么改实现（把 `^` 换成 `**` 再 parse），要么改文案。

### 10.3 坑：工具名和类名不一样

| 类名 | 实际 `name` |
|------|------------|
| `CalculatorTool` | `python_calculator` |
| `TerminalTool` | `terminal` |
| `SearchTool` | `web_search` |
| `ReadFileTool` | `read_file` |
| `RememberTool` | `remember_memory` |
| `RecallTool` | `recall_memory` |
| `ForgetTool` | `forget_memory` |

调用 `invoke_tool()` 时用的是 `name`，不是类名。想按类名调用会拿到 `未找到名为 'CalculatorTool' 的工具`。

**建议**：需要在运行时按名字找工具时，先 `list_names()` 看一眼，别猜。

### 10.4 坑：`global_registry` 是全局单例

模块级 `global_registry = ToolRegistry()` 会在**第一次 import 时**创建，进程内共享。多 Agent / 多测试用例共用时，A 注册的工具会污染 B。

**建议**：除了最简 demo，一律 `ToolRegistry()` 自己 new。

### 10.5 坑：可变默认值共享

`tags: List[str] = []` 和 `metadata: Dict[str, Any] = {}` 是**类属性**。`ToolBase.__init__` 里已经做了 `list(tags)` / `dict(metadata)` 拷贝，所以正常路径没问题。但如果你写子类时**绕过 `__init__`** 直接往 `type(self).tags` 里 append，就会污染所有实例。

**建议**：子类要么在类属性里写好初始值让 `__init__` 去拷，要么显式 `super().__init__(tags=[...])`。

### 10.6 坑：记忆工具与测试的导入路径

- `memory_tool.py` 的 docstring 写 `from fast_agents.memory import MemoryManager, build_memory_tools`；
- 实际 `fast_agents/memory/__init__.py` **不导出** `RememberTool` / `RecallTool` / `ForgetTool` / `build_memory_tools`；
- 正确路径是 `from fast_agents.tools.builtin import build_memory_tools`。

**修法二选一**：① 改 docstring 和 `test_memory.py` 的导入路径；② 把三个工具名补进 `memory/__init__.py` 的 `__all__`（但这会造成 `tools` → `memory` → `tools` 的循环导入风险，因为 `memory_tool.py` 已经 `from ...memory.manager import MemoryManager`，不推荐）。

### 10.7 坑：`tool_input` 传字符串时的 JSON 解析

`invoke()` 和 `invoke_tool()` 都支持把 JSON 字符串当参数传。但两者行为**不完全一致**：

- `ToolBase.invoke()`：`json.loads` 用 `except Exception` 兜住，**解析失败静默当成空 dict**（`parsed = {}`）；
- `ToolRegistry.invoke_tool()`：只捕获 `json.JSONDecodeError`，**会返回 `ToolResult.fail("参数不是合法 JSON...")`**。

也就是说，同一个坏 JSON，走 `invoke()` 是「参数缺失」错误，走 `invoke_tool()` 是「JSON 非法」错误。排查时注意这个差异。

### 10.8 坑：hook 抛异常会被吞掉

`invoke_tool()` 里每个 hook 都是 `try/except` + `logger.exception`，**不会中断主流程**。好处是观察代码写坏了不影响工具运行；坏处是 hook 静默失效，容易以为没触发。

### 10.9 坑：`return_direct` 目前只是个标记

`return_direct` 字段在 `ToolBase` / `StructuredTool` / `tool()` 里一路透传，但 `tools/` 和 `react_agent.py` 里**没有任何代码读它**。也就是说它现在只是元数据，不会真的让工具结果直接结束 Agent 循环。

### 10.10 跨平台注意事项

工具模块里有两处明确依赖操作系统，重点说。

**① `TerminalTool` 的命令白名单是 Unix 风格**

`_READONLY_COMMANDS` 里的 `ls` / `cat` / `head` / `tail` / `grep` / `find` / `pwd` / `which` / `whoami` 在 **Windows 上大部分不存在**（Windows 对应的是 `dir` / `type` / `findstr` / `where` 等）。集合里只有 `dir` 一个 Windows 命令。

后果：在 Windows 上让 Agent 用终端工具，它调 `ls` 会返回 `命令未找到：ls`。

**建议**：
- 要给 Windows 用，构造时传 `allowed_commands={"type", "findstr", "where", "more", "tree", "powershell"}` 之类补充；
- 或者干脆在 Windows 上别注册 `TerminalTool`，用 `ReadFileTool` 代替。

**② `TerminalTool._exec()` 的 `shell=True` 分支**

```python
needs_shell = any(sym in " ".join(parts) for sym in ("|", ">", "<", "*", "?", "&&", ";"))
```

含这些符号就走 `shell=True`。但在 Windows 上：

- `shell=True` 走的是 `cmd.exe`，**不认识 Unix 的 `|` 组合里常见的一些命令**；
- `shlex.split()` 是 **POSIX 规则**，Windows 路径里的反斜杠会被当转义符吃掉。比如 `type C:\Users\a.txt` 经 `shlex.split` 后 `C:\U...` 的反斜杠会消失或变形。

**建议**：Windows 上尽量用不含反斜杠的相对路径，或者用 `ReadFileTool` 代替读文件类命令。真要跑复杂命令，用 `allow_exec=True` 调 `powershell -Command`。

**③ 路径沙箱在三个平台都成立**

`ReadFileTool` 和 `TerminalTool` 用的都是 `Path.relative_to()` 做越界检查，不涉及字符串拼接，**这一点是跨平台安全的**。

**④ 编码**

- `ReadFileTool` 用 `utf-8` + `errors="replace"` 读文件：读 GBK 编码的中文文本会出替换符，但不会崩。Windows 上如果文件是记事本存的 ANSI（GBK），读出来是乱码状替换符。
- `TerminalTool._exec()` 用 `subprocess.run(..., text=True)` **没有指定 encoding**，Python 会用系统默认编码（Windows 下常是 GBK）。所以中文输出在 Windows 上通常能正常显示，但在其他组合下可能乱码。跨平台场景建议显式传 `encoding="utf-8"`。

**⑤ 换行符**

`ReadFileTool` 用 `splitlines()` 切行，对 CRLF / LF 都正确，不用管。
