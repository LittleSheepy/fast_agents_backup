# FastAgents 演进路线图（按模块）

> 面向 `fast_agents` 从「单 ReAct + 记忆」走向「完整 Agent 框架」的分模块建设计划。
> 本文**按模块组织**，每个模块给出四件事：**现状 → 目标 → 任务清单（优先级 / 依赖 / 验收） → 关键设计**。
> 与 [`记忆模块编写说明.md`](./记忆模块编写说明.md)（讲已完成的记忆实现）互补：这份文档只讲「还没做的、以及怎么做」。

## 一、现状快照

先盘清家底，路线才不会跑偏。下面的成熟度基于当前仓库的真实代码：

| 模块 | 现有实现 | 成熟度 | 主要缺口 |
|---|---|---|---|
| `llm/` | `LLM` 门面 + `OpenAIClient`，`invoke` / `stream_invoke` | 🟢 可用 | 无 `embed()`、无超时重试、只支持单一协议 |
| `messages/` | `Message` / `Messages`，原生支持 `tool_calls`，to_openai_message 正确处理 tool_call_id | 🟢 可用 | —— |
| `tools/` | `ToolBase`（pydantic `args_schema` 自动出 schema，`$ref` 内联）+ `ToolRegistry.invoke_tool` 统一入口（JSON/dict/kwargs 三形式）+ `ToolResult` 三态（SUCCESS/ERROR/TRUNCATED）+ 4 种定义方式（继承类 / @tool / StructuredTool.from_function / 裸函数）+ 计算器 / 终端 / 搜索 / 读文件 4 个内置工具 + 多 provider schema（OpenAI/Anthropic/Gemini）+ 同步/异步 invoke/ainvoke + hook 机制 | 🟢 基础完成 | 缺写/改文件、RAG、并行调用、审批、超时熔断 |

| `agents/` | `ReActAgent`（工具 + 记忆唯一实现，system 注入一次、工作区/历史分层、ToolResult 感知） | 🟡 单范式 | 无 Plan-Execute / Reflection / 子代理 |
| `skill/` | 无 | 🔴 未开始 | 全部 |
| `mcp/` | 无（`tools/__init__.py` 里 `MCPTool` 仅注释占位） | 🔴 未开始 | 全部 |
| `context/` | 散落在 buffer 摘要与 agent 工作区中 | 🟡 零散 | 无 token 预算、无工具结果卸载、无文件系统 |
| `infra/` | 无 | 🔴 未开始 | 无追踪、无评估、无异步、未发包 |

> **图例**：🟢 已可用 / 🟡 有基础待补 / 🔴 未开始。

**一个现成的路线图线索**：你的 `tools/__init__.py` 里已经注释掉了 HelloAgents 的整套工具清单（`SearchTool` / `RAGTool` / `NoteTool` / `MCPTool` / `A2ATool` / `ANPTool` / 四类评估工具）。这份清单其实就是一份现成的待办表——下面把其中值得做的挑出来，按模块归位。

## 二、推荐节奏：三个阶段

不必齐头并进，按「底座 → 能力 → 生产化」推进：

| 阶段 | 主题 | 模块 | 判断标准 |
|---|---|---|---|
| **阶段一** | 夯实底座 | `tools` 统一协议 + SearchTool；`memory` 短期落盘；`context` token 计数；`llm` 补 `embed()` | Agent 能联网搜索、长对话不丢历史、跑得稳 |
| **阶段二** | 扩展能力 | `skill` 从零建；`mcp` 接入；`agents` 加 Planner；`context` 加文件系统 | 能加载技能、能接第三方工具、能做长任务 |
| **阶段三** | 生产化 | `infra` 追踪与评估；`agents` 子代理/协作；`memory` 画像/多租户 | 可观测、可评估、可发布 |

## 三、模块 A：tools（工具系统）

### 现状（v3 · API 对齐 LangChain、清理所有兼容层）
- 基类统一命名为 **`ToolBase`**（**注意不是 `BaseTool`**），入参模型字段统一为 **`args_schema`**（pydantic BaseModel，旧版叫 `param_model`），调用入口统一为 **`invoke(tool_input=None, **kwargs) -> ToolResult`**（对齐 LangChain Runnable 协议，支持 dict/JSON 字符串/kwargs 三种传参形式）；
- 返回值统一为 **`ToolResult`**（`ok / fail / truncated` 三态 + `artifact` 结构化副产品），不再有旧的「裸字符串返回」兼容路径；
- 注册表统一入口 **`ToolRegistry.invoke_tool(name, tool_input, **kwargs)`**，返回 ToolResult；旧的 `execute_tool`（返回字符串的兼容函数）**已彻底删除**；
- 单个工具导出 `to_openai_tool / to_anthropic_tool / to_gemini_tool`，批量导出 `to_openai_tools / to_anthropic_tools / to_gemini_tools`（统一用 `to_` 前缀，符合 Python 序列化惯例）；
- 参数 schema 自动从 pydantic `args_schema` 或函数签名内省生成，嵌套 BaseModel / Enum 的 `$ref` 会被递归内联（OpenAI/Anthropic 不支持 `$defs`，内联避免参数缺失）；
- 四种定义方式齐备：继承 ToolBase / `@tool` 装饰器 / `StructuredTool.from_function` / 裸函数直接注册；
- 内置 4 个工具：`CalculatorTool`（AST 白名单）、`TerminalTool`（只读命令白名单 + 路径沙箱 + `allow_exec` 开关）、`SearchTool`（DuckDuckGo 默认 / 可切 Tavily）、`ReadFileTool`（路径沙箱 + 行区间 + 二进制黑名单 + 大文件自动截断）；
- 同步/异步双入口：`invoke/ainvoke`，hooks：`_before_run/_after_run/_on_error`，注册表级 `add_hook`，`tags/metadata/return_direct/max_output_chars/handle_tool_error` 配置齐全；
- Agent 侧感知 ToolResult.status：ERROR 前缀提示模型重试、TRUNCATED 自带「请缩小查询范围」提示。

API 命名全面对齐 LangChain 行业标准（`args_schema` / `invoke` / `to_openai_tool` 均与 LangChain BaseTool 一致），**无任何兼容层残留**。详细使用见 [`工具模块编写说明.md`](./工具模块编写说明.md)。

### 目标
从「能调一个函数」升级到「可治理的工具生态」：**补齐写/改类工具、RAG、并发、审批、熔断、可观测**。

## 四、模块 B：memory（记忆系统）

### 现状
**当前最成熟的模块**，已经有两层完整实现：
- 短期：`BufferMemory`（滑动窗口 + LLM 滚动摘要）；
- 长期：`MemoryStore` 抽象 + `InMemoryStore` / `SQLiteMemoryStore`，支持审计式 `revise` / `retract`、`user` / `session` 两级作用域、偏好无条件召回；
- 门面：`MemoryManager`（`retrieve` / `render_context` / `record` / `remember` / `forget`）；
- 工具：`remember_memory` / `recall_memory` / `forget_memory`。

详细实现见 [`记忆模块编写说明.md`](./记忆模块编写说明.md)。剩下的是**三块补丁**。

### 目标
补齐「短期落盘 + 语义检索 + 用户画像」，让记忆从「能用」到「生产级」。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **B1** | `SessionStore`：短期记忆落盘 | **P0** | — | 进程重启后 `buffer` 能自动恢复上次会话 |
| **B2** | `SemanticMemoryStore`：embedding 检索 | P1 | `llm.embed()` | 同义改写能召回（「住哪」↔「所在地」） |
| **B3** | `ProfileStore`：结构化用户画像 | P1 | — | pydantic schema 约束字段，覆盖式合并 |
| **B4** | 双通道注入（偏好进 system 末尾） | P1 | — | 稳定偏好常驻 system，召回记忆进 user |
| **B5** | 记忆衰减与合并 | P2 | B2 | 低重要度 + 久未命中自动归档/合并 |
| **B6** | 多租户 `tenant_id` | P2 | — | 所有查询强制带租户过滤 |

### 关键设计

**B1 · SessionStore（最该先做的一块）**
`buffer` 现在纯内存，进程一重启会话就没了——这是当前最明显的空缺。做法：

```python
# 复用 MemoryStore 的抽象思路，新增一张消息表
# sessions(session_id, seq, role, content, created_at)
class SessionStore:
    def load(self, session_id: str) -> list[Message]: ...
    def append(self, session_id: str, message: Message) -> None: ...
    def clear(self, session_id: str) -> None: ...
```

`BufferMemory` 加一个 `persist_store` 可选参数：`append()` 时同步落库，构造时 `load()` 回填。**上层接口不变**，`ReActAgent` 不用改。

**B2 · 语义检索**
`base.py` 的 `MemoryStore` 接口**不用动**（`search()` 已就位），只需新增 `SemanticMemoryStore`：
- 写入时对 `content` 算 embedding 存下来；
- 检索时对 query 算 embedding，做余弦相似度；
- 与现有 `scoring.py` 的词法分、重要性、时间衰减**加权融合**（保留现有融合结构，只是把「词法分」换成「语义分」或两者相加）。

前置动作：给 `LLM` 加一个 `embed(texts) -> list[list[float]]` 方法。

## 五、模块 C：skill（技能系统）· 从零新建

### 现状
**无**。这是与 MCP 并列的两大扩展方向之一，也是当前主流框架（Claude、DeepAgents、Microsoft Agent Framework）都在收敛的机制。

### 目标
实现 **Agent Skills 标准**：用「文件夹 + `SKILL.md`」封装领域知识与工作流，按需**渐进式加载**，避免把所有指令一股脑塞进 system prompt。

### 核心机制：渐进式披露（Progressive Disclosure）

这是 skill 的灵魂，三级加载：

| 层级 | 加载内容 | 时机 | token 成本 |
|---|---|---|---|
| **① Discovery** | 每个 skill 的 `name` + `description` | 会话启动 | 约 50–100 / skill（100 个也只占 ~5k） |
| **② Activation** | 完整 `SKILL.md` 正文 | 任务匹配时 | 约 500–2000 / skill |
| **③ Execution** | `scripts/` / `references/` / `assets/` | 真正用到时 | 按需 |

**和 memory 的分工**：memory 存「**事实/偏好**」（数据），skill 存「**怎么做**」（程序）。两者都是给上下文补信息，但一个是被调用的数据，一个是被加载的流程。

### 建议的落地形态

```
skills/
└── web-research/
    ├── SKILL.md          # 必需：YAML frontmatter(name, description) + Markdown 指令
    ├── references/       # 可选：参考文档
    └── scripts/          # 可选：可执行脚本
```

```markdown
---
name: web-research
description: 联网检索并汇总成结构化报告。当用户要求「查一下 / 调研 / 最新进展」时使用。
---
# 执行流程
1. 用 search 工具检索 3-5 条来源
2. 交叉验证，标注冲突
3. 输出「结论 + 来源」结构
```

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **C1** | Skill 数据模型 + `SKILL.md` 解析 | P1 | — | 能解析 YAML frontmatter（`name` / `description`） |
| **C2** | `SkillRegistry`：扫描 `skills/` 目录发现技能 | P1 | C1 | 启动时列出全部技能的 name + description |
| **C3** | 三级渐进式加载 | P1 | C1,C2 | catalog 进 system；激活读全文；再按需读 resources |
| **C4** | `ListSkillsTool` + `ReadSkillTool` | P1 | C2,C3 | Agent 能主动 `list_skills` / `read_skill` |
| **C5** | 示例技能包 | P2 | C1–C4 | ≥2 个可运行示例（如 `web-research`、`code-review`） |

> **实现落点**：`ReadSkillTool` 本质就是个「按名字读文件」的工具，和模块 F 的文件系统工具天然复用一个读取能力。

## 六、模块 D：mcp（协议接入）· 从零新建

### 现状
**无**。`tools/__init__.py` 里 `MCPTool` 只是一行注释。

### 目标
接入 **MCP（Model Context Protocol）**，让 Agent 能用任意 MCP server 提供的工具，**不用为每个工具单独写适配**。2026 年 MCP 已是事实标准（CrewAI、Vercel AI SDK、Mastra、Microsoft Agent Framework 均原生支持），接它就等于接入了一个庞大的现成工具生态。

### 关键设计

MCP 用 **JSON-RPC 2.0**，支持三种传输：`stdio`（本地子进程）/ `SSE`（旧）/ `Streamable HTTP`（推荐）。**最小闭环路线**：

1. 先只做 **stdio transport** + 两个方法 `list_tools` / `call_tool` —— 就能连本地 server 跑通；
2. 把每个 MCP tool **包装成 `ToolBase` 子类**（schema 直接用 MCP 返回的 `inputSchema`），注册进 `ToolRegistry` —— **Agent 侧完全无感知**，这就是 MCP 的价值；
3. 再加 HTTP transport 与配置发现。

> **两条实现路线**：想省事，直接用官方 `mcp` Python SDK 当 client；想理解原理（更契合你这个学习型项目的定位），自己写 JSON-RPC 也就一百来行。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **D1** | `MCPClient`（stdio transport） | P1 | — | 能连本地 stdio server 并 `list_tools` |
| **D2** | `MCPTool` 适配器（MCP tool → `ToolBase`） | P1 | D1 | 动态生成 schema，`call_tool` 正确映射 |
| **D3** | Streamable HTTP transport | P1 | D1 | 能连远程 http server |
| **D4** | `.mcp.json` 配置加载 | P2 | D3 | 启动自动发现、连接、打印「已加载 N 个工具」 |
| **D5** | 连接生命周期 + 错误重连 | P2 | D4 | 断线自动重连，单次调用失败不崩溃 |

## 七、模块 E：agents（范式与协作）

### 现状
只有 `ReActAgent` 一个范式（`agent_base.Agent` 已提供抽象基类）。

### 目标
补齐主流范式，并从「单 Agent」走向「协作」。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **E1** | `PlanExecuteAgent`（先规划再执行） | P1 | — | 先产出结构化步骤列表，再逐步执行 |
| **E2** | `ReflectionAgent`（自省修正） | P2 | — | 生成 → 自评 → 修订闭环 |
| **E3** | Sub-agent 子代理（隔离上下文） | P2 | E1 | 主 Agent 能派生独立上下文的子任务 |
| **E4** | 多智能体协作（Group / Handoff） | P2 | E3 | 两个 Agent 能传递任务、汇总结果 |
| **E5** | Agent 接口统一、范式可插拔 | P1 | — | 各范式实现同一基类接口，可互换 |

### 关键设计

**E1 · Planner**：ReAct 是「边想边做」，长任务容易跑偏或漏步骤。Plan-and-Execute 先让 LLM 产出一份结构化计划（JSON 步骤列表），再逐步执行，每步后可选择性重规划。落地：复用现有 `agent_base.Agent` 抽象 + `ToolRegistry` + 记忆。

**E3 · Sub-agent（参考 DeepAgents）**：子代理用**独立的上下文窗口**执行子任务，**只把结果**返回给主 Agent。好处是主 Agent 的上下文不被子任务的中间过程污染——这正是 DeepAgents 处理长任务的三大手法之一（规划、文件系统、子代理委派）。实现上就是「在工具里再跑一个 Agent」。

## 八、模块 F：context（上下文工程）

### 现状
`BufferMemory` 有滚动摘要，`ReActAgent` 有工作区管理，但都**停在局部**，没有全局的上下文视角。

### 目标
把「上下文」当一等公民对待：**有预算、有卸载、有文件系统**。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **F1** | `TokenCounter` + 上下文预算 | **P0** | — | 每次调用前算出 token 数，超预算自动裁剪 |
| **F2** | 工具结果卸载到磁盘 | P1 | F1 | 大结果写文件，只把引用/摘要给 LLM |
| **F3** | 文件系统工具（`ls`/`read`/`write`/`edit`） | P1 | — | Agent 能读写工作目录内的文件 |
| **F4** | 摘要/压缩中间件化 | P2 | F1 | 压缩策略可插拔（截断 / 摘要 / 卸载） |
| **F5** | Prompt caching 友好布局 | P2 | — | 静态段在前、动态段在后，可打缓存断点 |

### 关键设计

**F1**：为什么不先做这个不行？因为**「裁不裁」的前提是「知道有多少」**。现在 `buffer` 按「消息条数」裁剪，但一条消息可能是 3 个 token，也可能是一整篇文档。有了 token 计数，才能按**预算**而非条数管理。实现上可以先用 `tiktoken` 近似，无需精确。

**F3 · 文件系统（参考 DeepAgents）**：给 Agent 一个文件系统，它就能把「会话状态」外化成文件，这是长任务的关键能力。最小实现 4 个工具：`ls` / `read_file` / `write_file` / `edit_file`，**限定在 workspace 目录内**（安全边界）。它顺带还能支撑模块 C 读取 skill 的 `resources`。

可调试、可评估、可发布。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **G1** | `TraceLogger`：全链路记录 | P1 | — | LLM/工具/决策的输入输出 + 耗时落盘 |
| **G2** | 异步与并发 | P2 | A6 | 支持 async 调用、多工具并发 |
| **G3** | 评估工具（LLM Judge / Win Rate） | P2 | G1 | 能对两个 Agent 的输出打分对比 |
| **G4** | 打包发布 PyPI | P1 | — | `pip install fast-agents` 可安装使用 |
| **G5** | CI（测试 + lint） | P1 | — | push 自动跑测试 |

### 关键设计

**G1 · TraceLogger（参考 HelloAgents）**：相当于 Agent 的「黑匣子」。最小实现：一个全局 `Tracer`，在 `LLM.invoke` 和工具执行处各打一个点，记 `{时间戳, 类型, 输入, 输出, 耗时, session_id}` 落成 `jsonl`。出问题时能**回放**整条链路——这也是 G3 评估的数据基础。

## 十、模块依赖关系

```
llm.embed() ─────────────► memory(B2 语义检索)
                                │
                                └────► tools(A5 RAGTool)

tools ──┬──► skill(C4 需要工具注册)
        └──► mcp  (D2 适配器产出 ToolBase)
                        │
context(F1 token 计数) ─┼──► tools(A4 结果截断)
                        └──► memory(B4 双通道注入)

agents(E1 Planner) ──► agents(E3 子代理) ──► agents(E4 协作)

infra(G1 追踪) ──► 横切全局，无前置依赖
```

**先做无依赖、且被多处依赖的**：`F1`（token 计数）、`B1`（会话落盘）、`llm.embed()`、`G1`（追踪）——这四项是其他任务的公共地基。
