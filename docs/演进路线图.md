**两条容易看漏的事实**

## 四、模块 A：tools（工具系统）

### 现状（基线 `6c4bb1a`）

- 基类统一命名为 **`ToolBase`**（**注意不是 `BaseTool`**），入参模型字段统一为 **`args_schema`**（pydantic `BaseModel`，旧版叫 `param_model`），调用入口统一为 **`invoke(tool_input=None, **kwargs) -> ToolResult`**，支持 dict / JSON 字符串 / kwargs 三种传参形式；
- 返回值统一为 **`ToolResult`**（`ok` / `fail` / `truncated` 三态 + `artifact` 结构化副产品），不再有「裸字符串返回」兼容路径；
- 注册表统一入口 **`ToolRegistry.invoke_tool(name, tool_input, **kwargs)`**，返回 `ToolResult`；旧的 `execute_tool`（返回字符串）已删除；
- 单个工具导出 `to_openai_tool / to_anthropic_tool / to_gemini_tool`，批量导出 `to_openai_tools / to_anthropic_tools / to_gemini_tools`；
- 参数 schema 从 pydantic `args_schema` 或函数签名内省生成，嵌套 `BaseModel` / `Enum` 的 `$ref` 会递归内联（OpenAI/Anthropic 不支持 `$defs`）；
- 四种定义方式齐备：继承 `ToolBase` / `@tool` 装饰器 / `StructuredTool.from_function` / 裸函数直接注册；
- 内置 4 个工具：`CalculatorTool`（AST 白名单，**工具名是 `python_calculator`**）、`TerminalTool`（只读命令白名单 + 路径沙箱 + `allow_exec` 开关）、`SearchTool`（DuckDuckGo 默认 / 可切 Tavily）、`ReadFileTool`（路径沙箱 + 行区间 + 二进制黑名单 + 大文件截断）；
- 同步/异步双入口 `invoke / ainvoke`；hooks：`_before_run / _after_run / _on_error`，注册表级 `add_hook`；`tags / metadata / return_direct / max_output_chars / handle_tool_error` 配置齐全；
- Agent 侧感知 `ToolResult.status`：ERROR 前缀提示模型重试、TRUNCATED 自带「请缩小查询范围」提示。

详细实现见 [`工具模块编写说明.md`](./工具模块编写说明.md)。

从「能调一个函数」升级到「可治理的工具生态」：**补齐写/改类工具、RAG、并发、审批、熔断、可观测**。

## 五、模块 B：memory（记忆系统）

### 现状

**当前最成熟的模块之一**，`fast_agents/memory/` 共 8 个文件：

- 短期：`buffer.py` 的 `BufferMemory`（滑动窗口 + LLM 滚动摘要）；
- 长期：`base.py` 的 `MemoryStore` 抽象 + `in_memory_store.py` / `sqlite_store.py`，支持审计式 `revise` / `retract`、`user` / `session` 两级作用域、偏好无条件召回；
- 门面：`manager.py` 的 `MemoryManager`（`retrieve` / `render_context` / `record` / `remember` / `forget`）；
- 打分：`scoring.py` 的词法分 + 重要性 + 时间衰减（半衰期 30 天，权重 0.6 / 0.3 / 0.1）；
- 工具：`remember_memory` / `recall_memory` / `forget_memory`（在 `tools/builtin/memory_tool.py`）。

详细实现见 [`记忆模块编写说明.md`](./记忆模块编写说明.md)。剩下的是**三块补丁**。

### 目标

补齐「短期落盘 + 语义检索 + 用户画像」，让记忆从「能用」到「生产级」。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **B1** | `SessionStore`：短期记忆落盘 | **P0** | — | 进程重启后 `buffer` 能自动恢复上次会话 |
| **B2** | `SemanticMemoryStore`：embedding 检索 | P1 | `llm.embed()` | 同义改写能召回（「住哪」↔「所在地」） |
| **B3** | `ProfileStore`：结构化用户画像 | P1 | — | pydantic schema 约束字段，覆盖式合并 |
| **B4** | 双通道注入（偏好进 system 末尾） | P1 | — | 稳定偏好常驻 system，召回记忆进 user |
| **B5** | 记忆衰减与合并 | P2 | B2 | 低重要度 + 久未命中自动归档/合并 |
| **B6** | 多租户 `tenant_id` | P2 | — | 所有查询强制带租户过滤 |
| **B7** | 统一两个 Store 的 `search()` 打分口径 | P1 | — | 见 [H6](#十一模块-hdefects已发现缺陷修复清单)：同一 query 换后端召回顺序不再变化 |

### 关键设计

**B1 · SessionStore（最该先做的一块）**

`buffer` 现在纯内存，进程一重启会话就没了——这是当前最明显的空缺。做法：复用 `MemoryStore` 的抽象思路，新增一张消息表，

```python
# sessions(session_id, seq, role, content, created_at)
class SessionStore:
    def load(self, session_id: str) -> list[Message]: ...
    def append(self, session_id: str, message: Message) -> None: ...
    def clear(self, session_id: str) -> None: ...
```

`BufferMemory` 加一个 `persist_store` 可选参数：`append()` 时同步落库，构造时 `load()` 回填。**上层接口不变**，`ReActAgent` 不用改。

**B2 · 语义检索**

`base.py` 的 `MemoryStore` 接口**不用动**（`search()` 已就位），只需新增 `SemanticMemoryStore`：写入时对 `content` 算 embedding 存下来；检索时对 query 算 embedding 做余弦相似度；与现有 `scoring.py` 的词法分、重要性、时间衰减**加权融合**。

前置动作：给 `LLM` 加一个 `embed(texts) -> list[list[float]]` 方法。

## 八、模块 E：agents（范式与协作）

### 现状

只有 `ReActAgent` 一个范式（`agent_base.AgentBase` 已提供抽象基类），已内置记忆与技能。

> **注意**：真实基类名是 `AgentBase`（在 `fast_agents/agents/agent_base.py`），不是 `Agent`。`agents/react_agent/` 下**没有** `__init__.py`。

### 目标

补齐主流范式，并从「单 Agent」走向「协作」。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **E1** | `PlanExecuteAgent`（先规划再执行） | P1 | — | 先产出结构化步骤列表，再逐步执行 |
| **E2** | `ReflectionAgent`（自省修正） | P2 | — | 生成 → 自评 → 修订闭环 |
| **E3** | Sub-agent 子代理（隔离上下文） | P2 | E1 | 主 Agent 能派生独立上下文的子任务 |
| **E4** | 多智能体协作（Group / Handoff） | P2 | E3 | 两个 Agent 能传递任务、汇总结果 |
| **E5** | Agent 接口统一、范式可插拔 | P1 | — | 各范式实现同一基类接口，可互换 |
| **E6** | `agents/react_agent/__init__.py` | P2 | — | 补齐包初始化文件，支持 `from fast_agents.agents.react_agent import ReActAgent` |

### 关键设计

**E1 · Planner**：ReAct 是「边想边做」，长任务容易跑偏或漏步骤。Plan-and-Execute 先让 LLM 产出一份结构化计划（JSON 步骤列表），再逐步执行，每步后可选择性重规划。落地：复用现有 `AgentBase` 抽象 + `ToolRegistry` + 记忆。

**E3 · Sub-agent**：子代理用**独立的上下文窗口**执行子任务，**只把结果**返回给主 Agent，主 Agent 的上下文不被子任务的中间过程污染。实现上就是「在工具里再跑一个 Agent」。

## 九、模块 F：context（上下文工程）

### 现状

`BufferMemory` 有滚动摘要，`ReActAgent` 有工作区管理（`_seed_workspace`），但都**停在局部**，没有全局的上下文视角。

### 目标

把「上下文」当一等公民对待：**有预算、有卸载、有文件系统**。

### 任务清单

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| **F1** | `TokenCounter` + 上下文预算 | **P0** | — | 每次调用前算出 token 数，超预算自动裁剪 |
| **F2** | 工具结果卸载到磁盘 | P1 | F1 | 大结果写文件，只把引用/摘要给 LLM |
| **F3** | 文件系统工具（`ls`/`read`/`write`/`edit`） | P1 | — | Agent 能读写工作目录内的文件 |
| **F4** | 摘要/压缩中间件化 | P2 | F1 | 压缩策略可插拔（截断 / 摘要 / 卸载） |
| **F5** | Prompt caching 友好布局 | P2 | — | 静态段在前、动态段在后，可打缓存断点 |

### 关键设计

**F1**：为什么不先做这个不行？因为**「裁不裁」的前提是「知道有多少」**。现在 `buffer` 按「消息条数」裁剪，但一条消息可能是 3 个 token，也可能是一整篇文档。有了 token 计数，才能按**预算**而非条数管理。实现上可先用 `tiktoken` 近似，无需精确。

**F3 · 文件系统**：给 Agent 一个文件系统，它就能把「会话状态」外化成文件，这是长任务的关键能力。最小实现 4 个工具：`ls` / `read_file` / `write_file` / `edit_file`，**限定在 workspace 目录内**（安全边界）。它顺带还能支撑模块 C 读取技能的 `references/`。

## 十二、模块依赖关系

```
llm.embed() ─────────────► memory(B2 语义检索)
                                │
                                └────► tools(A7 RAGTool)

tools ──┬──► skills(C6 脚本沙箱可复用 TerminalTool 的白名单思路)
        └──► mcp  (已完成，D2 适配器产出 ToolBase)

context(F1 token 计数) ─┬──► tools(A4 结果截断)
                        └──► memory(B4 双通道注入)

agents(E1 Planner) ──► agents(E3 子代理) ──► agents(E4 协作)

infra(G1 追踪) ──► 横切全局，无前置依赖
```

**先做无依赖、且被多处依赖的**：`H4`（依赖补齐）、`F1`（token 计数）、`B1`（会话落盘）、`llm.embed()`、`G1`（追踪）——这五项是其他任务的公共地基。
